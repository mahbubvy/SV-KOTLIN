# `.svbackup` Kotlin Importer — Technical Handoff

**Purpose:** guide a separate native Android/Kotlin app to import encrypted SecretVault backup version 1 (`SVBACK01`) safely and compatibly.

**Scope:** read/import existing `.svbackup` archives only. This document does not authorize changing the format, adding export, replacing the destination app's vault encryption, or altering either app's unlock/security policy. Implement one phase at a time. Do not mark compatibility complete from compilation alone.

## Reference implementation

Use these K-drive SecretVault files as the current source of truth:

- `src/services/vault-backup.ts` — production v1 writer and verifier.
- `src/services/vault-backup-manifest.ts` — current shared production manifest validation.
- `src/services/vault-restore.ts` — production restore orchestration and staging behavior.
- `scripts/backup-prototype/format.mjs` — independent Node format encoder/decoder and exact cryptographic construction.
- `scripts/backup-prototype/format.test.mjs` — vectors and malformed archive cases.
- `modules/cmf-high-fps-camera/android/src/main/java/expo/modules/cmfhighfpscamera/BackupFormatSelfTest.java` — synthetic Android crypto compatibility self-test only. It is **not** the production archive importer.
- `docs/Backup-Build52-Test.md` and `docs/improvement/I1.2c-backup-export-completion.md` — current test/recovery caveats.

Never depend on unpublished file paths in the receiving app. Give its coding agent this handoff and a sanitized test archive plus its test password through a secure channel. The archive/password are fixtures; do not commit secrets or personal media.

## Non-negotiable rules

1. Preserve the version 1 byte contract below exactly. Do not call it ZIP, guess fields, normalize strings, or “improve” the cryptography in place.
2. `.svbackup` is encrypted with a **backup password**, separate from the source phone's PIN, biometric state, permanent vault key, `.svenc` media encryption key, and `.svtransfer` receiver key. Do not import or store those other secrets.
3. Treat the picker URI, archive bytes, manifest, filenames, sizes and dates as untrusted, even after decryption. Authentication proves bytes were made with the password/key; it does not make the archive safe or valid for this app.
4. Stream large media. Never read the archive/video in full into a `ByteArray`, Base64 string, bitmap, or heap-sized buffer.
5. Write decoded bytes to app-private staging. Do not expose restored rows/files until every record, final summary and EOF has validated. On any error/cancel, preserve existing vault data and remove only files owned by this import attempt. If the target app cannot commit all items transactionally, journal attempt-owned files and recover on next launch.
6. Never overwrite a pre-existing file based only on an archive-provided display name or ID. Generate destination storage IDs according to the receiving app's own rules.
7. Keep backup passwords out of logs, analytics, crash reports, saved preferences and persistent job journals. Clear mutable key/password buffers when their lifetime ends. A JVM `String` cannot be reliably zeroed; minimize its lifetime and copies.
8. Keep v1 read compatibility. A later archive format must use a new explicit version/migration path, not relaxed parsing of v1.

## Exact v1 wire contract

All multi-byte integers are unsigned, big-endian. Reject unsupported parameters and integer overflow before allocating memory or creating staging output.

### Header: exactly 32 bytes

| Offset | Bytes | Meaning |
|---:|---:|---|
| 0 | 8 | ASCII `SVBACK01` |
| 8 | 4 | PBKDF2 iteration count; must equal `600000` |
| 12 | 4 | media chunk size; must equal `262144` bytes (256 KiB) |
| 16 | 16 | random per-archive PBKDF2 salt |

### Key derivation

- Password is non-empty exact UTF-8, with **no trimming, case folding, or Unicode normalization**.
- Maximum encoded password length: 1,024 UTF-8 bytes.
- PBKDF2-HMAC-SHA256, 600,000 iterations, 256-bit output key.
- Verify the Kotlin `SecretKeyFactory` provider's result against a known vector generated by the reference Node `pbkdf2Sync(passwordUtf8, salt, 600000, 32, "sha256")`. `PBEKeySpec` accepts chars; do not assume every provider encodes non-ASCII characters identically. If the provider fails the non-ASCII vectors, implement/use a reviewed PBKDF2-HMAC-SHA256 path that consumes the exact UTF-8 bytes. Do not silently transform the user's password.
- Do not persist the derived backup key. This key is not the destination vault's encryption key.

### Record framing and authentication

Records follow consecutively until the final record; there is no outer container or per-file marker. Each record is:

| Field | Bytes | Meaning |
|---|---:|---|
| Type | 1 | `1` manifest, `2` media chunk, `3` final summary |
| Index | 4 | zero-based record sequence number |
| Ciphertext length | 4 | plaintext length; excludes the 16-byte GCM tag |
| Sealed bytes | length + 16 | AES-GCM ciphertext followed by its 16-byte tag |

For each record index `i`:

1. Nonce is 12 bytes: eight zero bytes followed by `i` as unsigned 32-bit big-endian.
2. AAD is byte concatenation `header[32] || recordHeader[9] || previousTag[16]`.
3. `previousTag` is 16 zero bytes for record 0; after successful authentication, it becomes this record's tag.
4. Use AES-256-GCM with a 128-bit authentication tag (`AES/GCM/NoPadding`, `GCMParameterSpec(128, nonce)`). Java `Cipher.doFinal(ciphertext || tag)` can return plaintext when provider conventions match; test this with known vectors.
5. Indices begin at 0 and increase by exactly one, including the manifest and final record. Reject duplicates, gaps, reorderings, and wraparound before using the nonce.
6. Reject a bad GCM tag. Do not expose unauthenticated plaintext to the vault or UI. Any streaming provider behavior must be verified: some APIs can output bytes before final tag validation; those bytes are provisional staging only and must be deleted on failure.

### Record types and mapping

1. **Manifest (`type=1`, index 0):** one UTF-8 JSON payload, at most 16 MiB. Decode UTF-8 strictly; reject malformed JSON and unexpected structure.
2. **Media (`type=2`):** plaintext bytes for each manifest item in manifest order. Each item's size determines its chunk count: `ceil(size / 262144)`. Chunks are full-size except the last chunk. A zero-byte item has no media record. There is no item ID in each media record; the manifest order and declared sizes define ownership.
3. **Final summary (`type=3`):** authenticated UTF-8 JSON exactly representing the count/total, e.g. `{"items":N,"bytes":TOTAL}`. Require values to equal the validated manifest and bytes consumed.
4. After the final summary, require true EOF. Reject missing final record, partial header/body/tag, extra bytes/records, and any content after the final record.

### Manifest v1

Top level: `version: 1`, ISO-style parseable `createdAt`, `albums[]`, and `items[]`.

Each album has `id`, `name`, `kind` (`system` or `custom`), `createdAt`, and optional/null `coverItemId`. Current SecretVault validation limits albums to 10,000, IDs to 1–80 chars, names to non-blank and at most 80 chars, and requires unique IDs and case-insensitive trimmed names. System albums must match known system ID/name pairs.

Each item has UUID-shaped `id`, `albumId`, `originalFilename`, `mediaType` (`photo` or `video`), `mimeType`, `size`, and parseable `createdAt`. Current validation limits items to 100,000, filename to 1–512 chars, MIME type to at most 255 chars, requires unique IDs and an existing album, and requires non-negative safe-integer sizes with a safe total. A cover must reference a photo in that same album.

Use `src/services/vault-backup-manifest.ts` as the precise current writer/reader contract. Also apply receiver-side safety: never interpret `originalFilename` as a path, sanitize display text for the target UI, enforce destination filename rules locally, and do not trust MIME type/extension as proof of file content. Do not broaden acceptance just because JSON parses.

## Phased implementation plan

### Phase 0 — Inventory the receiving app and freeze scope

1. Locate the other app's Kotlin package, vault model, metadata store, media encryption service, import/picker flows, and existing tests.
2. Identify its established duplicate policy, album merge rules, destination ID generation and durable-publication/rollback mechanism. Do not assume they match SecretVault.
3. Write down which restore behavior is needed: merge into the current vault, create a separate destination vault, or both. Use the app's existing behavior if already defined; flag a product ambiguity before implementing that branch.
4. Keep change limited to v1 archive reading and import. No change to archive writer, PIN/biometric, secret storage, existing media encryption format, share intents, cloud sync, or UI redesign.

**Exit gate:** short architecture note identifies insertion points and proves the importer will not overwrite existing user data on error.

### Phase 1 — Build compatibility fixtures and crypto vectors

1. Generate a tiny archive with `scripts/backup-prototype/format.mjs`; include one photo, one video, a custom cover, and an empty album.
2. Add fixtures/password vectors: ASCII; leading/trailing spaces; accented text; non-Latin text; emoji; composed/decomposed Unicode as distinct passwords. Include exact UTF-8 byte length boundaries (1,024 accepted if valid; 1,025 rejected by creation/reference policy).
3. Record expected derived-key bytes and decrypted media SHA-256 outside the production APK. Store only synthetic media and test passwords in test resources.
4. Verify the Kotlin JCA provider against these reference outputs before designing restore around it. Test Node writer -> Kotlin decode early.
5. Add malformed fixtures: wrong magic/parameters, invalid lengths, wrong sequence/type, wrong password, changed header/record/tag, truncation at every record boundary, absent final record, bad summary, trailing bytes.

**Exit gate:** Kotlin can derive the exact key and authenticate/decrypt the fixture. Non-ASCII and spacing compatibility is proven, not inferred.

### Phase 2 — Implement a bounded streaming parser

1. Define a small reader over `InputStream`/`ContentResolver` URI with `readFully` and EOF detection. Handle SAF streams that do not support seeking; never depend on `available()` for total length or EOF.
2. Parse fixed-size header and record fields with explicit unsigned-to-`Long` conversion. Validate values and checked arithmetic before allocating.
3. Parse/authenticate/decrypt one record at a time. Keep bounded memory: header + record header + tag/state + at most one 256 KiB media chunk + bounded manifest. Do not buffer the full archive.
4. Enforce the exact record grammar/index/AAD/nonce chaining and maximum manifest size. Reject index overflow before nonce reuse.
5. Separate parsing from vault mutation: produce typed metadata/chunk callbacks into a staging abstraction, never call the final database commit from the crypto primitive.
6. Ensure GCM tag failure discards the current provisional output and causes the entire import attempt to fail. Check cancellation between reads/records and during long staging copies.

**Exit gate:** parser tests pass all valid/invalid framing and cryptographic vectors with strict memory bounds.

### Phase 3 — Validate manifest and map to destination models

1. Parse JSON with bounded input; reject unknown or malformed required fields and duplicate IDs/names per current v1 contract.
2. Validate count/length/date/type/size/cover relationships before creating large staging output. Check total bytes and disk-space policy safely.
3. Validate each original filename as display metadata; never use it for path construction. Generate app-owned storage filenames/IDs.
4. Map system albums explicitly. Keep unknown system album IDs from silently becoming privileged/system entries; choose a safe custom/fallback mapping according to the receiving app's documented behavior.
5. Define duplicate detection using the target app's existing product rules. Never overwrite media by display filename. Preserve source album placement where possible; document cases the target model cannot represent.

**Exit gate:** adversarial manifests fail before publication; valid albums, cover, dates, filename display values and sizes map correctly.

### Phase 4 — Stage and publish safely

1. Use the target app's app-private staging directory and own every staged file by an import-attempt ID.
2. Stream each authenticated plaintext chunk to its staged item file or directly into the target app's existing encryption writer. Never write plaintext to shared storage, Downloads, logs, or cache with a longer lifetime than necessary.
3. Decide whether re-encryption into the destination app's own media encryption is required. It usually is: `.svbackup` encryption protects the archive with the backup password; it is not the receiver's at-rest media format. Never treat decrypted archive payload as already encrypted `.svenc` data or reuse the source phone's key.
4. Complete final-record and EOF validation before committing any metadata. If a later item fails, remove only this attempt's staged outputs; leave existing vault files/index unchanged.
5. Publish using a database transaction or the app's durable journal/commit protocol. If multiple filesystem moves cannot be atomic, persist recovery ownership first and reconcile after process death. Do not delete a destination file whose metadata may already have committed.
6. Handle low disk space, provider read error, revoked URI permission, cancellation, process death and duplicate races. Report a partial/uncertain outcome honestly if the OS/provider prevents cleanup.

**Exit gate:** wrong password, corruption, cancellation and injected write/publication failure cause zero visible partial imports; repeat import follows the specified duplicate behavior.

### Phase 5 — Add the user import flow

1. Add a narrow `.svbackup` document-picker entry; use the Android Storage Access Framework URI as a stream. Do not request broad storage permission solely for this picker.
2. Ask for the backup password after the user selects a candidate archive. Preserve spaces exactly; show/hide is optional but must not alter the value. Do not persist password or derived key.
3. Show meaningful progress stages (opening, validating, importing, complete), item counts where known, and a cancellable operation. Do not claim progress is based on total archive file size if it is not.
4. Keep existing unlock/lock semantics. If the app locks/backgrounds during import, continue only according to the target app's existing authenticated-job policy; never silently unlock it on return.
5. Use neutral errors that distinguish wrong password/damaged file from unavailable destination where possible without logging sensitive archive content.

**Exit gate:** normal picker/password/import flow works on a physical Android device; cancel and picker dismissal do not modify the vault.

### Phase 6 — Prove cross-app and recovery compatibility

Required matrix:

| Case | Expected result |
|---|---|
| SecretVault v1 writer -> Kotlin importer, ASCII password | Imports exact photo/video bytes and metadata |
| Same with leading/trailing spaces and non-ASCII password | Imports; demonstrates exact KDF/password compatibility |
| Photo + multi-chunk video + multiple albums + empty album + custom cover | Counts, bytes, dates and relationships preserved |
| Empty archive / zero-byte item | Correctly handled without phantom media records |
| Wrong password / header or tag tampering | Reject, no visible import |
| Truncated record / missing final summary / invalid summary / trailing bytes | Reject, no visible import |
| Invalid manifest / oversized count or integer / unsafe name | Reject safely, bounded memory and no path escape |
| Cancel, URI revoked, low space, write failure | Existing vault unchanged; attempt-owned staging cleaned or recovery journal retained |
| Existing content duplicate and same display filename with different bytes | Target duplicate policy followed; never overwrite by display name |
| App process killed during staging and around commit | Restart recovery leaves consistent metadata/files and permits safe retry |

Add at least one **production SecretVault APK archive** created from synthetic data, not only a fixture generated by the Node prototype. For strong bidirectional confidence, test Kotlin-produced output only if a writer is separately requested; import-only work does not require adding an exporter.

Compare restored plaintext media SHA-256 to source fixtures before the receiving app re-encrypts them; after re-encryption, verify by reading through the target app's normal decryption/playback path. Confirm large video plays through its end with sound where present.

**Exit gate:** test report names device/build, archive source, password class (never the password), media size/count, and pass/fail. A mocked parser test alone is not device/SAF/crash-recovery evidence.

### Phase 7 — Release and handoff

1. Run the receiving repository's tests, static checks and Android release build; record exact commands and results.
2. Update-install on a disposable/test installation first. Never uninstall/clear the only vault to get around signing or migration failures.
3. Test on at least two Android versions/storage providers if available, including a large video and a non-ASCII password.
4. Record accepted v1 behavior, known limitations, APK/version/source commit and rollback/recovery path.
5. Do not call the entire archive format “verified” until production archives, Unicode KDF, SAF streams, malformed input and process interruption have evidence.

**Exit gate:** release notes and test matrix completed; pre-existing vault remains readable after upgrade and failed imports.

## Test engineering guidance

- Prefer deterministic golden files and output hashes for format compatibility. Random salts mean two newly generated archives should differ even for equal inputs/passwords.
- Keep cryptographic tests separate from filesystem/publication tests. Inject stream, crypto, staging and metadata boundaries; do not mock away the record parser/AES construction in the primary interoperability test.
- Fuzz lengths, record index, type, count, integer overflow, UTF-8/JSON parsing and truncation without allowing huge allocations.
- Include exact chunk boundaries: 0, 1, `CHUNK_SIZE - 1`, `CHUNK_SIZE`, `CHUNK_SIZE + 1`, multiple chunks, and empty album/media cases.
- Test final GCM failure after earlier valid chunks: no item may become visible.
- Never include personal user media/passwords in repository fixtures, screenshots, CI artifacts or crash reports.
- Use synthetic files with known hashes and realistic large streamed videos for performance/memory tests.

## Explicitly out of scope unless separately requested

- Writing `.svbackup` files from the Kotlin app.
- Changing the v1 binary format, KDF iteration count, AES mode, record framing or filename convention.
- Importing a source-device PIN, biometrics, Keep Unlocked flag, device key, lock screen, or weather-decoy settings.
- Reusing `.svbackup` as the destination app's encrypted media-at-rest format.
- Importing `.svenc`, `.svtransfer`, ZIPs, ordinary document formats or unrelated private-vault formats.
- Upload/cloud sync/network service, background server, or broad storage permission.
- Replacing the receiver's metadata database or camera/media architecture as part of importer work.
